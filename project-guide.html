Your stochastic modeling project

Build a small, reproducible analysis that explains what could happen, how sure you are, and which choice the evidence supports.

Work individually or in a pair. Use two or three complementary methods in total: a simple baseline, at least one stochastic model, and an optional extension. Depth, validation, and clear interpretation matter more than the number of models.

Start with a measurable question

Specify the system, unit of observation, time horizon, outcome, and choice to compare. A useful question is: “Using earlier daily rental counts, how well can we predict days above a planning threshold, and how does the estimated exceedance risk change between thresholds of 4,000 and 5,000 rentals per day?” Both thresholds are scenario assumptions; they are not measured bike-system capacities.

Let $X_t$ be the observed number of completed rentals on day $t$ and $Y_t(c)=\mathbf{1}\{X_t>c\}$. Two possible metrics are the exceedance probability $P(X_t>c)$ and expected excess $E[(X_t-c)_+]$, where $(x)_+=\max(x,0)$. A binary model can estimate the first but does not identify the second without a model for counts above the threshold.

Keep the claim within the measurement.

Completed rentals do not measure all desired trips, station shortages, fleet size, or wait times. A threshold comparison is a conditional planning exercise. Estimating how an actual capacity change would alter demand needs additional data and causal assumptions.

Use the Module 1 lesson and companion notebook to begin with a documented outcome, a training estimate, a simulation, and a later-period check. Extending that same example is a valid full project.

For a possible next step, use Module 2 and its Markov-chain notebook to ask whether today’s demand state improves predictions. Define the states before evaluation, estimate transitions from consecutive training days, and compare the chain with the same empirical-rate baseline. This is an optional extension of the same sustained project.

Module 3 and its stationarity and hitting-time notebook offer two further optional metrics: the fitted chain’s stationary high-demand fraction and the probability of first reaching a high-demand day within a fixed window. The first describes a time-homogeneous model’s long-run behavior; it is not a promise about a changing season. The second requires a stated initial state and window, and validation must use only windows whose outcomes are fully observed. Overlapping windows are dependent.

Module 4 and its Monte Carlo notebook add a precision check to an existing model or scenario comparison. Define one independent replication, choose a simulation budget, and report Monte Carlo error conditional on the fitted parameters. More simulated paths do not add observed bike-rental days or resolve uncertainty about the state definition. This is a refinement of the same project.

Module 5 and its MCMC notebook calibrate the same two transition hazards with independent Beta priors, using the 242 transitions wholly within January–August. Compare Metropolis–Hastings output with the available conjugate posterior before interpreting it. Trace plots, autocorrelation, basic split $\widehat R$, and mean MCSE help diagnose the computation but do not establish model adequacy or guarantee convergence. Propagate posterior parameter uncertainty into a relevant prediction, and keep it distinct from computational MCSE and process variability. September–December remains a reused development holdout, not a fresh test. This is an optional refinement of the same project; MCMC is unnecessary when exact posterior sampling already answers the question.

Module 6 and its branching notebook distinguish growth in an ensemble mean from survival of an individual population. Use an offspring model only when parent–offspring relationships and generations are meaningful. A synthetic offspring sample illustrates how a Gamma–Poisson posterior changes finite-horizon extinction; it is not a fit to the bike data. The bike exercise instead audits a conditional count model using January–August pairs and later chronological observations. Daily completed rentals are not generations or offspring, and this comparison cannot establish transport-system extinction. Module 6 completes Part B of the same Lab 3 due in week 6.

Module 7 and its Poisson-process notebook return to observed daily counts. Estimate constant and working-day calendar rates using January–August only; freeze them and compare later predictions with persistence on the same September–December dates. Use residual dispersion and time structure to question Poisson assumptions. Daily totals identify integrated daily intensity under the model; they do not identify exact rental times, within-day peaks, unmet demand, or service delays. Synthetic rate profiles demonstrate the timing distinction without claiming observed arrival records. Module 7 begins Lab 4 Part A; Module 8 completes Part B for one submission in week 8. Use this as an optional count-model comparison within the same sustained project.

Module 8 and its renewal and continuous-time notebook compare renewal gaps, conditional residual waits, and state-dependent exponential holding times. A finite bike-station birth–death model is a synthetic scenario: capacity, return rates, and rental-attempt rates are assumed, not calibrated from daily system totals. Weight state visits by elapsed time when estimating continuous-time occupancy. The real-data audit counts observed days, rental totals, means, and zero-count days separately for January–August and September–December. These daily system totals contain no station identifiers, inventory, return records, attempted rentals, or event timestamps; they do not identify renewal gaps or continuous-time station rates. Adopt these methods only when the project has the necessary timing and state observations. Module 8 completes Lab 4 Part B, submitted once with Module 7 Part A in week 8.

Module 9 and its queueing notebook connect congestion, service variability, and discrete-event simulation. Check a hand trace, compare an event calendar with Lindley’s recursion, and verify stable M/M/1 and M/D/1 benchmarks with independent replication means. January–August completed-rental volume supplies only a scale for a hypothetical maintenance queue: the referral fraction, operating hours, arrival law, and service rates are assumptions. Later daily counts provide a descriptive comparison of observed volume across the chronological split; they do not validate maintenance arrivals or waiting times. A real queueing study needs arrival, service-start, and completion timestamps with queue discipline and observation boundaries. Module 9 starts Lab 5 Part A; submit it once with Module 10 Part B in week 10. The existing model/validation checkpoint remains due in week 9; no new project is introduced.

Module 10 and its Brownian dynamics notebook separate stochastic variability, Monte Carlo error, time-step error, and model discrepancy. Check Brownian scaling, compare exact geometric Brownian motion with Euler–Maruyama under the same noise, and refine nested grids. Fit daily log-growth parameters only to the 242 January–August increments, then freeze them for 122 rolling one-day forecasts in September–December using the actual previous day. Compare conditional means with persistence and report interval coverage and increment diagnostics. The positive continuous model is a count proxy, not evidence that completed rentals follow a physical diffusion; negative lag-one dependence and seasonal changes challenge its independent, stationary increment assumptions. The later period remains a reused development holdout. This completes Lab 5 Part B for one combined submission with Module 9 in week 10 and adds no new project.

Module 11 and its Gaussian-process notebook use covariance kernels to express dependence and Cholesky solves to calculate conditional predictions. The bike demonstration estimates only a training mean and scale from 243 January–August counts, then compares prespecified RBF length scales of 14 and 45 days with amplitude 1 and observation-noise standard deviation 0.5 in standardized units. All 122 September–December forecasts are fixed at August 31, with no later observations or refits; the baselines use the training mean and last training value throughout. This is a different information protocol from Module 10’s rolling one-day forecasts, so their aggregate scores are not a like-for-like model ranking. Separate latent-function intervals from intervals for new noisy observations; both condition on plug-in settings and omit uncertainty in the fitted mean, scale, and kernel parameters. A Gaussian observation approximation may permit negative counts and does not establish a count-generating mechanism. Use the later data to diagnose coverage and extrapolation as reused development evidence, without selecting a setting and calling that same period a fresh test. Module 11 begins Lab 6 Part A; combine it with Module 12 Part B for one submission in week 12, within the existing project workload.

Module 12 and its validation and sensitivity notebook compare a rolling GP, persistence, and a weekly-lag baseline on matching one-day targets. Use 181 January–June days as initial history, select an RBF length scale of 14 or 45 days by MAE over the 62 July–August targets, and freeze that choice before the 122 September–December targets. At each origin the GP uses the previous 60 counts and fits centering and scaling from that earlier window only; amplitude 1 and noise SD 0.5 remain chosen standardized assumptions. Later windows update using observations already available at the origin. Baseline predictive scales use only past errors. Compare point accuracy, Gaussian predictive density, a stated 4,500-rentals event, and interval quality. Stress predictive SD and block length when estimating uncertainty in paired losses; a block bootstrap is an approximation requiring suitable dependence assumptions. September–December remains reused assessment, not a pristine test. This rolling protocol differs from Module 11’s fixed-origin forecasts, so earlier scores cannot rank the model families directly. Complete Lab 6 Part B and submit once with Module 11 Part A in week 12; use the same sustained project.

Module 13 and its reproducibility and verification notebook support the final refinement of this same project. The worked audit revisits the two-state bike chain at the declared 4,000-rentals threshold, checks exact probabilities against simulation, and compares frozen-matrix rolling one-day forecasts with persistence. An audit of one component does not replace the project’s two or three meaningful methods. Record the data source and checksum, units, chronological information boundary, model assumptions, software environment, and random-number setup so another student can rerun the work. Use independent invariants, analytical benchmarks, and deliberately flawed claims to verify computations. Repeating a seeded result does not establish that the model is adequate, and passing code checks does not create new validation data. Keep the bike sample’s later dates labeled as reused development evidence. Document consequential AI assistance together with the checks, corrections, and limitations; all activities work without an AI account. Use the existing week 13 project allocation to improve the decision brief and rehearse the individual explanation; there is no seventh lab or additional project.

Module 14 and its presentations and explanations notebook bring the same analysis into a 6-minute presentation and an individual explanation. Link the central claim to a declared question, executed result, validation comparison, uncertainty, and limitation. The worked bike-chain example revisits existing calculations: observed counts, fitted transition probabilities, exact conditional probabilities, and a calculated conditional simulation-precision reference are different kinds of evidence. This final module generates no new simulated paths. An assumed transition change does not establish the effect of changing bike capacity. Rehearse explaining one formula and figure, tracing or modifying a short code cell, and checking a consequential AI-style claim; no AI account is needed. Keep the notebook, 4–5 page report, one-page brief, and slides consistent. This synthesis introduces no new required method, concept lab, or project.

A high-demand flag in the bike data can return to a lower-demand state. Making it absorbing is a calculation for a stopped first-hit experiment, not a claim that high demand persists forever. The module’s four-state operational example is entirely synthetic: its states and transition probabilities are assumptions, not measured bike capacity, shortages, or service outcomes. Use it to verify computation; a real operational claim needs suitable observations.

The required data audit

Include a compact table with these fields in the proposal and update it in the final notebook:

  • Identity: dataset title, creator, direct source URL/DOI, original filename, version or retrieval date, license/reuse link, attribution, and local file checksum.
  • Measurement: what one row represents, collection process, population/location, date range, timestamp/time-zone convention if known, sampling interval, variables, units, and missing-value codes. Mark undocumented items as unknown.
  • Preparation: original and retained row counts; filtering, sorting, duplicate handling, missing-data treatment, aggregation, and a reproducible transformation from source to sample.
  • Limits: selection bias, censoring or truncation, missing periods, proxy outcomes, and quantities absent from the data. State which questions cannot be answered.
  • Use: planned training/validation/test dates, information available at prediction time, legal redistribution status, and where the frozen sample and attribution will live.

Bundle a small sample when redistribution is permitted. Otherwise provide an accessible retrieval/preparation recipe and explain the access limitation; do not redistribute restricted rows. Keep observed data separate from simulated outputs in filenames, captions, and code variables.

The minimum complete analysis

Keep the course examples comparable

The daily completed-rental count is written as X or C, and its binary state as Y or S. Modules 1–5 use a strict 4,000-rental threshold; Modules 13–14 use an inclusive one. No bundled count equals 4,000, so their observed states coincide, but the boundary convention must remain explicit in new data. Module 12 deliberately uses a different 4,500-rental event. Do not compare Brier scores across different event definitions.

Module 11 makes all later predictions from August 31. Modules 10 and 12–14 instead use rolling one-day origins; Module 12 also selects settings on July–August and updates only from earlier observations. A shared dataset does not make scores comparable when information, horizons, targets, or loss functions differ. Every project comparison must match those quantities.

  1. Define the outcome. State the question, prediction or decision horizon, metric with units, and what success would look like. Fix thresholds before inspecting the test outcome.
  2. Prepare and inspect observations. Complete the audit, visualize time order and missingness, and identify dependence or regime changes that affect modeling.
  3. Set a baseline. Use an empirical rate, persistence predictor, seasonal average, or other transparent comparator. Fit the baseline and the stochastic model using the same allowed training information.
  4. Fit a stochastic model. Write the mathematical definition and assumptions directly before estimation code. Explain the parameter units, estimators, state choices, and how sparse or unavailable information is handled.
  5. Verify simulation. Use fixed seeds for reproduction, vary seeds to show Monte Carlo variability, and compare at least one mean, probability, or limiting case with a known analytical result. Check nonnegative rates and normalized probabilities.
  6. Validate against observations. Evaluate baseline and model on the same held-out periods with a relevant score and one diagnostic plot. Tune using training/validation data and reserve a final untouched test period when feasible. The bundled September–December sample has already been used across the course, so a project extending it must label it as reused development assessment, report that limitation, and specify a future validation plan; it must not call those dates a fresh final test. Obtain genuinely new observations before claiming untouched-test performance. Preserve time order and refit only on information available at each prediction origin. For a Markov chain, distinguish a fixed-origin forecast, which advances the last known state distribution using $P^h$, from rolling $h$-step forecasts, which use the observed state at each new origin. Keep the fitted transition matrix fixed unless the evaluation protocol explicitly permits refitting; compare methods on identical target dates at each horizon.
  7. Compare at least two scenarios. Define precisely what changes, what is held fixed, and whether the scenario value is measured or assumed. Report the difference in a decision metric and its uncertainty.
  8. Stress the conclusion. Vary an influential parameter, modeling assumption, or training window. Identify when the preferred scenario changes or when the evidence is too weak to choose.
  9. Communicate and reproduce. Explain what the evidence supports, what it cannot establish, and how another student can rerun the complete analysis.
Distinguish four sources of uncertainty.

Process variability is the spread of future outcomes even if the model and its parameters are known. Monte Carlo uncertainty comes from finitely many simulation runs; parameter uncertainty comes from finite observations; model uncertainty concerns assumptions and omitted mechanisms. More simulation reduces Monte Carlo error, not the variability of the real process. State what each interval includes.

For an estimated scenario mean from independent simulation replications $Y_1,\ldots,Y_N$, use $\hat\mu=N^{-1}\sum_rY_r$ and $\widehat{\mathrm{SE}}(\hat\mu)=s_Y/\sqrt N$. If you use dependent MCMC output, this formula requires an autocorrelation adjustment. If you resample temporally dependent observations, justify a block or model-based method rather than treating days as independent by default.

For independent paired scenario replications, define $\Delta_r=Y_r^{(B)}-Y_r^{(A)}$ and use $s_\Delta/\sqrt N$ for the Monte Carlo standard error. Common random numbers reduce the difference variance when they induce positive covariance; improvement is not guaranteed. A changed transition probability remains a scenario assumption unless supported by appropriate measurements and causal evidence.

If a relevant event is rare, ordinary importance sampling averages $g(Y_r)f(Y_r)/q(Y_r)$ for independent draws from $q$. The proposal must cover every outcome where $g(y)f(y)\ne0$; correct weights give an unbiased estimate when the target expectation exists. Check finite variance, weighted contributions, and an analytical benchmark before trusting a standard error. Dividing by the observed sum of weights changes the estimator and generally loses finite-sample unbiasedness. An observed zero-event sample does not establish a zero event probability.

A reproducible handoff

  • Place definitions and formulas immediately before their related computation; use short cells and descriptive variable names with units.
  • Use relative paths and a frozen permitted data sample, or a documented retrieval/preparation script. Record package versions and explain any added dependency.
  • Keep observed values, fitted quantities, and synthetic simulations visibly distinct. Save seed choices and simulation sizes; explain why a different seed changes a numerical estimate.
  • Include meaningful checks: dimensions, nonnegative rates, transition row sums, theoretical moments, and limiting cases relevant to your model.
  • Restart the kernel and run all cells in order. Include the resulting figures and compact outputs, plus instructions sufficient for another student to repeat the run without hidden state or paid services.
  • Keep the report and brief consistent with the executed notebook; report limitations and uncertainty where the decision is stated.

Optional AI, mandatory verification

You may use AI for ideas, explanations, coding, and debugging. No paid account or live AI access is required. A provided flawed snippet can be used for every course verification exercise. Whether code came from you, a partner, a package, or AI, you remain responsible for explaining and testing it.

Log consequential assistance: date and tool, purpose/prompt summary, output adopted or rejected, changes you made, and evidence used to check it. The statement “No AI assistance used” is sufficient when applicable. Do not include invented sources or label a model-generated number as an observation.
